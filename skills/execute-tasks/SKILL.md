# Execute Tasks — one session per issue and verified commit loop

## Setup and safety
- This invocation authorizes completing approved tasks with local **code edits and coherent Git commits**; it does **not** authorize PR publication, issue closing, remote push, merge, release, production writes, or new goals.
- Load `AGENTS.md`, task plan, its exact source artifact (including the GitHub issue for maintenance), and actual git status. For an issue source, regenerate the canonical content digest described in the plan and reconcile only if `Source digest` changed; an `updatedAt`-only change is informational and does not block execution. Run one session per issue: other issues may run concurrently in their own worktrees, but never start a second run on the same issue or worktree. A run invoked by `$work-issue` in the same session is that issue's run; a run never spawns subagents itself. Preserve user changes; unexpected dirty paths beyond the approved plan handoff or an ambiguous base branch → ask before modifying.
- Verify `Plan approval: approved` and exact task IDs. Use [references/task-execution.md](references/task-execution.md) for exceptions and evidence format.
- Locate `scripts/taskctl.py` relative to this SKILL.md and call it by its resolved real path (for example, from `realpath`), not through a skills-directory symlink. Use the installed `python3` if available. Its status file is Git metadata, not a tracked source file. Commands must point to the **same approved plan** in every session.
- Run every Git command with the issue worktree as the working directory and no options before the subcommand (no `git -C`). Codex allowlist rules match command prefixes exactly.

## Branch ownership
- Issue-backed MAINTENANCE or OSS work requires **one feature branch per issue**. Never place planning or implementation commits on the base or create a separate branch for each task.
- MAINTENANCE: resolve the issue workspace with `taskctl.py workspace get --issue <N> --base <base>` from any checkout of the repository. It creates `.worktrees/issue-<N>` on the issue branch (default `fix/issue-<N>`) on first use and returns the same entry afterwards. Work only inside the returned `worktree`; never switch branches in another checkout. Then run `workspace claim --issue <N> --owner <session-id>` with an ID unique to this session (for example `<cli>:<host>:<start-time>`); when `$work-issue` already holds the claim, reuse its owner and leave the release to it. A claim held by another owner means another session owns the issue: stop and report it. Run `workspace release` with the same owner when all tasks are recorded or the run blocks or stops. Before `release --force` on a lease left by a stopped session, show `workspace list` and get the user's confirmation.
- A ledger that already exists in the current checkout for the same plan (started before workspaces) keeps using that checkout and branch.
- OSS: on first execution, identify the intended base and create the issue's feature branch from it, following repository naming conventions. If an existing branch belongs to the same issue, verify its scope and base from the plan, commits or PR before reusing it; the current branch or its name alone is not sufficient evidence. Choose a routine branch name without asking the user; ask only when issue ownership or the intended base is genuinely ambiguous.
- On resume, use the branch where implementation of that issue began. Its name is stored as `branch` in `git rev-parse --git-path agent-workflow/progress.json`. Inspect the existing ledger with `status` for the same approved plan before selecting a branch or running `init`. If needed, safely return to that branch while preserving user changes; do not create a replacement branch or overwrite the ledger. A missing branch or conflicting ledger requires reconciliation.
- For NEW PROJECT work, stay on the current branch unless the user or repository policy requests another branch.

## Entry / resume
1. Classify the approved plan and select the execution branch using the rules above. For MAINTENANCE, resolve and claim the workspace first; all later steps run inside it. Later sessions reuse the branch where that issue's implementation began.
2. If the only dirty path is a newly approved repository-local plan from `$plan-tasks`, commit it as a planning baseline on the selected execution branch and retain it. Keep an external OSS plan under git metadata without adding it. For issue work, if the plan was already committed on the base branch, stop for user-directed reconciliation rather than rewriting history.
3. With a clean checkout, run `python3 <this-skill>/scripts/taskctl.py init --plan <plan> --base-branch <base>` once for issue work. Omit `--base-branch` for NEW PROJECT work. This records the execution branch, optional base branch/SHA, baseline SHA, plan digest and storage mode. On resume, run `status` and then `next`; if a task is in progress, resume **that task**. If the plan hash changed, explain and use `sync-plan --approved` only after explicit approval and after committing the approved plan revision on the recorded branch.
4. Before starting a pending task, check repo clean, related code, dependencies and test strategy; run `taskctl.py start --plan <plan> --task TNNN`. For resumed task, inspect staged and unstaged changes and evidence; no blind reset/stash.
5. Implement only the selected scope. Prefer tests that prove acceptance criteria; include negative cases, regressions, DB/API compatibility, AI evaluation fixtures as applicable. Run **actual** required verification commands. Never edit tests just to hide real failures or claim tests were run when not.
6. Review `git diff` and `git diff --cached`: scope, secrets, unintended changes, migrations, docs, broken contracts, missing tests. Fix valid issues and rerun affected validation. When important requirements or architecture must change, **stop for user approval and reconcile the source requirements with the task plan**; do not edit a GitHub issue without separate authorization.
7. Only after all task acceptance/required checks pass, stage **intended paths only**, create one or more coherent local commits according to repo conventions. No `git add -A` if unrelated data exists. Record the final committed `HEAD` SHA. If a task needs multiple verified commits, only mark complete when final revision covers the full task.
8. Write a truthful JSON verification receipt to a temporary path following [references/task-execution.md](references/task-execution.md). Then run `complete`; this validates the receipt, HEAD and clean checkout, and stores progress outside tracked source. The helper records evidence but **cannot prove commands actually executed**; the agent must perform them.
9. Repeat `next` until all task commits are recorded. Run relevant **whole-plan** integration/regression checks, write a whole-plan receipt, and record it with `taskctl.py verify-plan --plan <plan> --evidence <path>`. Confirm `status` reports `whole_plan_verification: current`. If checks fail, investigate/revert to the impacted task or open a new user-approved plan; do not claim completion. Preserve the plan and ledger for later `$create-pr` evidence lookup, and release the workspace lease.

## Block behavior
- An unresolvable failure, unavailable test environment, unsafe change, or required approval: call `taskctl.py block --plan <plan> --task TNNN --reason "..."` and report it. **Do not start a different task**. After the blocker is resolved, `resume --plan ... --task TNNN` and retry that same task.
- Do not paper over failures by skipping verification. For inherently non-executable changes, record a concrete review/check command (`git diff --check`, etc.) and evidence rather than inventing test execution.
- `taskctl.py` has no automatic commit or remote write functionality; preserve user authorization and CLI permission boundaries.
